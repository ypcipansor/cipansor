# automation-self-trigger-loop

> An event automation whose trigger condition is "a new comment exists" will
> satisfy that condition with its own comment and re-arm itself. On #678 the
> `needs-info` re-check produced six back-to-back LLM runs from a single
> fixture, each one triggered by the previous run's output.

A comment-triggered automation and its own output are indistinguishable unless
the trigger is written to tell them apart. The defect is not in the comments;
it is in the trigger.

1. **An automation's comment satisfies `issue_comment.created`.** If the
   trigger also requires a label (`needs-info` present), the only thing keeping
   the cycle alive is that label staying on the issue. Remove the label and the
   loop stops — that is a mitigation, not a fix; the next genuinely
   `needs-info` issue re-arms it.

2. **`sender.login` cannot separate the automation when it posts as a human
   account.** The re-check posted as `adminypc`, the same account as the
   reporter, and `user.type` was `User` — so neither `sender.login` nor
   `sender.type == 'Bot'` marks it. The three filters that *do* work:

   - **Post from a distinct bot account** (e.g. `cipansor-bot`), then exclude
     it: `sender.login != 'cipansor-bot'`. Cleanest; the trigger never depends
     on comment wording.
   - **Exclude by the AI footer.** Every automated comment ends with
     `_This comment was generated by an AI agent (OpenHands) on behalf of …_`,
     so `!icontains(comment.body, 'generated by an AI agent')` breaks the loop
     with no account change.
   - **Fire on application, not on every comment.** Trigger on
     `issues.labeled` with `contains(issue.labels[].name, 'needs-info')` (the
     moment the label is applied) and, if a reply should also re-check, require
     a positive phrase in the reply. A `needs-info` label is applied once, so
     no comment the automation or anyone else posts can re-fire it.

3. **Do not rely on a human to stop it.** The re-check is a full LLM
   conversation per run; on #678 the cost was unbounded until the label was
   removed by hand. The trigger must be self-limiting by construction.

**Where the definition lives.** These are OpenHands event automations, not
files under git — a grep of `.github/`, `docs/`, `scripts/` and `.claude/` for
`needs-info` / `issue_comment` / `icontains` / JMESPath finds no trigger. The
change is a filter edit in the automation backend (OpenHands automations API),
outside this repository; a repo PR can document the rule but cannot apply it.
Read the trigger of a candidate automation with
`GET /api/automation/v1/{id}` and confirm the fix with
`GET /api/automation/v1/{id}`, then `POST …/{id}/dispatch` on a throwaway
issue before re-enabling it.

**Why it matters:** one fixture cost six runs, and any labelled issue can
consume unbounded runs on every automated comment. **How to apply:** before
enabling a comment-triggered automation, ask what its own output does to the
trigger; if the output satisfies it, add one of the three exclusions in point 2
— never ship the trigger unfiltered and rely on someone noticing.
