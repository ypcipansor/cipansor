# automation-triggers-are-untrusted-input

> An OpenHands event automation whose trigger fires on comments will fire on its
> own comments. On a `needs-info` issue the re-check armed itself six times in
> fifteen minutes — six full LLM runs, none from the reporter.

First seen 2026-10-07 on #678 (issue #680). The `needs-info` re-check automation
was built on `on: issue_comment.created` + a filter for the `needs-info` label.
Its own reply satisfies that filter, so each run posted the next run's trigger.
Every run is a full conversation, so the cost is unbounded, not a one-off.

## Why the obvious guards did not hold

- **`sender.login` cannot separate the automation from the reporter.** Automations
  post through the account that owns the run (`adminypc`, `user.type: User`), the
  same account a person replies from. `sender.type == 'Bot'` is false for it too.
- **The automation's comments are indistinguishable from a human's by metadata**,
  so identity alone cannot break the cycle; only the body or a distinct bot
  account can.
- **The trigger is not in this repository.** There is no checked-in definition of
  the `needs-info` re-check (confirmed by grep across `.github/`, `scripts/`,
  `docs/`, `.claude/`; #679 only adds unrelated label-sync tooling). No repo test
  can guard config that lives only in the automations backend.

## The guard that works

1. **Prefer a trigger that cannot see its own output.** Fire on `issues.labeled`
   (`contains(issue.labels[].name, 'needs-info')`) rather than on every
   `issue_comment.created`; an application is one run, a comment stream is not.
2. **If it must watch comments, exclude its own words.** Every automated comment
   ends with the mandated AI-disclosure footer. Add
   `!icontains(comment.body, 'generated by an AI agent (OpenHands)')` to the
   trigger filter. This is XS and needs no new account.
3. **Post as a distinct bot account** when a metadata guard is wanted
   (`sender.type == 'Bot'`), with a least-privilege secret allowlist — never
   every secret.
4. **Short-circuit inside the run too.** A trigger is data from an untrusted
   event, not a promise that the comment is human; a run that sees its own marker
   should stop before spending a conversation.

## The trap in fix #2

The footer is a literal string. Pin it exactly where the trigger is defined, and
note that if the wording changes the loop returns silently. Any future change to
the disclosure footer is also a change to this guard.

## What to check on any new event automation

- Does the trigger condition depend on something the automation's own output
  produces (a comment, a label it applies, a status it sets)? If yes, it re-arms.
- Is the automation's identity distinct from every human that can trigger it?
- Is the definition checked in anywhere a PR can change and test it? If not, the
  only place the guard exists is the backend — write the marker down here.
